**접속 방법 — 두 가지 중 하나**
```bash
# (권장) SSH 터널: 노트북 브라우저에서 http://localhost:8000/
ssh -L 8000:localhost:8000 wjs@10.20.135.134
# (간단) 직접 접속: 노트북이 같은 핫스팟에 있으면 http://10.20.135.134:8000/
```
> ⚠️ **노트북 마이크를 쓰려면 반드시 터널 방식**이어야 한다. 브라우저는 `localhost`나 `https` 주소에서만
> 마이크 사용을 허락하므로, `http://10.20.135.134:8000`으로 열면 마이크가 막힌다(0-3절).
> 터널은 기본 PIN이 0000인 앱을 핫스팟 전체에 노출하지 않는 장점도 있다.

**tmux로 서버 띄우기** (SSH가 끊겨도 서버는 계속 돈다)
```bash
tmux new -s kiosk                      # 세션 만들기
cd /mnt/ssd/projects/myproject
./scripts/start_ui.sh                  # 화면만 (PLAN 기준). 음성까지면 ./scripts/start_voice_ui.sh
#   Ctrl+B 누른 뒤 D  → 빠져나오기(서버 유지)
tmux attach -t kiosk                   # 다시 들어가기 (로그 보기 · Ctrl+C로 서버 종료)
tmux capture-pane -pt kiosk | tail -30 # 들어가지 않고 로그만 보기
tmux ls                                # 세션 목록
tmux kill-session -t kiosk             # 세션 끝내기
```
- `start_ui.sh`는 STT·TTS를 **띄우지 않는다**(떠 있으면 재사용만). 음성 작업 때는 `start_voice_ui.sh` 사용 —
  내비게이션이 떠 있으면 실행을 거부하므로 원격에서 로봇이 움직일 일이 없다.
- 수정 반영: 화면 파일(`src/`)은 **브라우저 새로고침**, 서버 코드(`kiosk_server.py`)는 tmux에서 Ctrl+C 후 재실행,
  TTS 서버 코드(`tts_server.py`)는 `pkill -f tts_server.py` 후 재실행(로딩 30초~2분).

#### 📝 노트북 음성 모드 구현 방법 (제안)
**원칙**: 키오스크 기본 동작(보드 마이크·스피커)은 그대로 두고, **주소에 `?audio=browser`를 붙였을 때만** 바뀐다.
```
[노트북 브라우저] ?audio=browser
  마이크 버튼 → getUserMedia(노트북 마이크) → 말 끝 감지(브라우저) → 녹음 파일 업로드
      → POST /listen (오디오 + lang) → 서버: ffmpeg로 16kHz WAV 변환 → whisper → 장소 매칭 → 기존과 같은 응답
  안내 음성 → POST /speak {text, id, lang, play:"browser"} → 서버: TTS로 WAV 생성 → 음성 파일을 응답으로
      → 브라우저 <audio>로 노트북 스피커 재생(재생 끝날 때까지 기다림 → 기존 "말 끝난 뒤 녹음" 순서 유지)
```
1. **녹음(화면, 새 파일 `src/js/recognizer/browserMic.js`)**
   - `navigator.mediaDevices.getUserMedia({audio:true})` + `MediaRecorder`(webm/opus).
   - 말 끝 감지: `AnalyserNode`로 소리 크기를 0.1초마다 재서 **서버 VAD와 같은 기준**(1.2초 무음이면 종료, 0.6초 미만 버림,
     최대 12초)을 적용. 시작 전 2초 버퍼는 "버튼 누른 순간부터 녹음"으로 대체.
   - `recognizer/index.js`에서 `?audio=browser`일 때만 이 인식기를 선택(기존 `real.js`는 그대로).
2. **서버 받기(`S:/listen`)**: 요청이 `audio/*`이면 본문을 임시 파일로 저장 → `ffmpeg -i in -ar 16000 -ac 1 out.wav`
   (보드에 ffmpeg n4.2.7 설치돼 있음) → 기존 `_whisper_transcribe` → 기존 매칭. JSON(`text` 주입)·본문 없음(보드 마이크)은 **기존과 동일**.
   임시 파일은 끝나면 지운다(현재 보드 녹음 파일 `/tmp/stt_input_*.wav`는 지우는 코드가 없음 — 함께 정리 권장).
3. **재생**: `tts_server.py`에 **음성 파일을 그대로 돌려주는** 요청 방식 추가(예: `POST /synth` + `{"return":"wav"}`).
   앱 서버 `/speak`는 `play:"browser"`이면 이것을 받아 `audio/wav`로 브라우저에 전달. 화면은 `robotController.speak()`에서
   받은 소리를 `new Audio(URL.createObjectURL(blob))`로 재생하고 `ended`까지 기다린다.
   - 기존 장치(대사별 허용 목록 `TTS_ONLY_FILE`, 오래된 요청 폐기, `/flush`)는 그대로 적용.
4. **녹음·재생 겹침 방지**: 기존 `_stt_lock`은 보드 장치용. 노트북 모드는 화면이 "재생 끝 → 녹음 시작" 순서를 지키므로 충분.
5. **확인**: 💻 노트북에서 마이크 권한 허용 → 말하기 → 인식 결과, 안내 음성이 노트북에서 들리는지.
   보드 기본 모드(주소에 `?audio=browser` 없음)가 그대로인지도 확인.

### 0-5. [항목 5·6] STT 다국어 구현 방법 (📝)

| 항목 | 값 | 노트북에 주는 의미 |
|---|---|---|
| SSH 서버 | 동작 중, 22번 포트 | 노트북에서 바로 접속 가능 |
| 설정 파일(`/etc/ssh/sshd_config`) | 따로 바꾼 줄 없음 → 우분투 기본값 | **비밀번호 로그인 허용**, **포트 전달(터널) 허용** |
| 사용자 / 호스트 이름 | `wjs` / `ubuntu` | |
| 보드 IP | `10.20.135.134` (폰 핫스팟, **바뀔 수 있음**) | 0-10-6 참고 |
| avahi(mDNS) | 동작 중 | `ubuntu.local` 이름으로 찾을 수 있을 **가능성** (노트북에서 확인 필요) |
| `~/.vscode-server` | **없음** | VS Code 원격 접속을 쓰면 보드에 새로 설치됨 → 0-10-5 주의 |
| 보드 eMMC 여유 | 1.8 GB (94% 사용) | 보드 홈 폴더에 큰 파일이 생기면 안 됨 |

#### 0-10-1. 준비물 (노트북)
| 준비물 | Windows 10/11 | macOS · Linux |
|---|---|---|
| SSH 프로그램 | 기본 내장(OpenSSH). PowerShell에서 `ssh -V`로 확인. 없으면 설정 → 앱 → 선택적 기능 → "OpenSSH 클라이언트" 추가 | 기본 내장 |
| 브라우저 | Chrome 또는 Edge (마이크 권한 처리가 같음) | Chrome |
| 같은 네트워크 | 노트북을 **보드와 같은 폰 핫스팟**에 연결 | 같음 |
| (선택) 편집기 | VS Code + "Remote - SSH" 확장 | 같음 |
| (노트북 음성 테스트 시) | 노트북 마이크·스피커(또는 이어폰), 브라우저 마이크 권한 | 같음 |

#### 0-10-2. 만들 파일 ① SSH 접속 설정 — `~/.ssh/config` (가장 중요)
- 위치: Windows `C:\Users\<내이름>\.ssh\config` (확장자 없음), macOS·Linux `~/.ssh/config`
- 폴더가 없으면 만든다(Windows: `mkdir $HOME\.ssh`).
```
Host jetson
    HostName 10.20.135.134          # 보드 IP (바뀌면 이 줄만 수정)
    User wjs
    Port 22
    # 노트북 브라우저 http://localhost:8000 → 보드 앱 서버 8000 (터널)
    LocalForward 8000 localhost:8000
    # 핫스팟이 잠깐 끊겨도 연결 유지 시도 / 죽은 연결 빨리 감지
    ServerAliveInterval 30
    ServerAliveCountMax 4
    # (키를 만든 경우만) 아래 줄의 # 지우기
    # IdentityFile ~/.ssh/id_ed25519
```
- 이후 접속은 `ssh jetson` 한 줄. 터널(8000)도 자동으로 열린다.
- 노트북에서 이미 8000번을 쓰는 프로그램이 있으면 `LocalForward 18000 localhost:8000`처럼 바꾸고 브라우저에서 `localhost:18000`.

#### 0-10-3. 만들 파일 ② 접속 단축 파일 (선택, 편의용)
**Windows** — 바탕화면에 `jetson.bat`:
```bat
@echo off
start "" "http://localhost:8000/"
ssh jetson
```
**macOS·Linux** — `~/jetson.sh` (만든 뒤 `chmod +x ~/jetson.sh`):
```bash
#!/bin/bash
( sleep 3; open "http://localhost:8000/" 2>/dev/null || xdg-open "http://localhost:8000/" ) &
ssh jetson
```
- 더블클릭(또는 실행)하면 SSH 창이 열리고 브라우저가 뜬다. SSH 창을 닫으면 터널도 닫히므로 **작업 중엔 SSH 창을 닫지 않는다**.
- 보드 서버가 아직 안 떠 있으면 브라우저에 "연결할 수 없음"이 나온다 → SSH 창에서 서버를 띄운 뒤(0-2절 tmux) 새로고침.

#### 0-10-4. (선택) 비밀번호 없이 접속 — SSH 키
비밀번호 로그인이 허용돼 있어 **안 해도 접속은 된다**. 매번 비밀번호 입력이 번거로울 때만:
```bash
ssh-keygen -t ed25519            # 노트북에서. 엔터 3번 → ~/.ssh/id_ed25519(.pub) 생성
```
- 공개키(`id_ed25519.pub`)를 보드의 `~/.ssh/authorized_keys`에 **한 줄 추가**해야 동작한다.
  ⚠️ 이건 **보드 파일을 바꾸는 일**이라 이번 원칙(보드 무변경) 밖이다. 하려면 따로 결정 후 진행
  (macOS·Linux는 `ssh-copy-id jetson`, Windows는 공개키 내용을 복사해 보드 파일 끝에 붙여 넣기).

#### 0-10-5. (선택) VS Code로 보드 파일을 직접 편집할 때 — 주의
- VS Code "Remote - SSH"는 처음 접속할 때 **보드 홈 폴더(`~/.vscode-server`, eMMC)에 수백 MB를 설치**한다.
  보드 eMMC 여유가 1.8 GB뿐이라 위험하다.
- 쓰려면 **노트북 VS Code 설정**(`settings.json`)에 설치 위치를 SSD로 지정한 뒤 접속한다:
```json
"remote.SSH.serverInstallPath": { "jetson": "/mnt/ssd/vscode-server" }
```
  → 그래도 보드 SSD에 파일이 생긴다(보드 무변경 원칙과 충돌). **원칙을 지키려면 VS Code 원격 대신 SSH 창 + 보드의 편집기
  (`nano`/`vim`)를 쓰거나, 편집은 Claude Code 세션에 맡긴다.**
- `~/.ssh/config`의 `Host jetson`을 VS Code가 그대로 읽으므로 따로 설정할 것은 없다.

#### 0-10-6. 보드 IP가 바뀌었을 때
핫스팟을 다시 켜면 보드 IP가 바뀔 수 있다. 노트북에서 찾는 방법(보드 무변경):
1. **이름으로 시도**: `ping ubuntu.local` → 응답이 오면 `~/.ssh/config`의 `HostName`을 `ubuntu.local`로 바꿔 두면 IP가 바뀌어도 된다.
   (Windows 10 일부 버전은 `.local`이 안 될 수 있음 — 그때는 2번)
2. **핫스팟 폰의 "연결된 기기" 목록**에서 `ubuntu`의 IP 확인 → `HostName` 수정.
3. 보드에 이미 SSH로 붙어 있다면 `ip -br -4 addr`로 확인(`wlan0`/`wlan1` 줄).

#### 0-10-7. 처음 연결 점검 순서 (노트북에서)
| 단계 | 명령 / 동작 | 정상이면 |
|---|---|---|
| 1 | `ping 10.20.135.134` (또는 `ping ubuntu.local`) | 응답이 온다. 안 오면 같은 핫스팟인지 확인 |
| 2 | `ssh jetson` → 비밀번호 입력 | 보드 프롬프트 `wjs@ubuntu:~$`. 첫 접속 때 "Are you sure…" → `yes` |
| 3 | (보드에서) `tmux new -s kiosk` → `cd /mnt/ssd/projects/myproject && ./scripts/start_ui.sh` → `Ctrl+B` `D` | 서버가 tmux 안에서 계속 돈다 |
| 4 | 노트북 브라우저 `http://localhost:8000/` | 키오스크 첫 화면("무엇을 도와드릴까요?") |
| 5 | `http://localhost:8000/?nurse=1` | PIN 입력 화면 |
| 6 | (노트북 음성 모드가 생긴 뒤에만) 마이크 버튼 → 브라우저 "마이크 허용" | 노트북 마이크로 녹음 — **현재는 아직 보드 마이크로 녹음됨**(0-3절) |

#### 0-10-8. 자주 생길 문제
| 증상 | 원인 | 해결(노트북 쪽) |
|---|---|---|
| `ssh: connect … timed out` | 다른 네트워크 / IP 바뀜 | 같은 핫스팟 연결, 0-10-6으로 IP 확인 |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 같은 IP를 다른 기기가 받음(핫스팟) | 노트북에서 `ssh-keygen -R 10.20.135.134` 후 재접속 |
| `bind … Address already in use` (8000) | 노트북에서 8000을 이미 사용 | `LocalForward 18000 localhost:8000`로 변경 |
| 브라우저 "연결할 수 없음" | 보드 서버가 안 떠 있음 / SSH 창을 닫음 | SSH 창 유지, 보드에서 `tmux attach -t kiosk`로 서버 확인 |
| SSH가 자주 끊김 | 핫스팟 절전·신호 | `ServerAliveInterval` 유지. 서버는 tmux 안이라 끊겨도 계속 돈다 → 다시 `ssh jetson`만 하면 됨 |
| 마이크 권한 창이 안 뜸 | `http://<IP>:8000`으로 접속함 | 반드시 터널 주소 `http://localhost:8000` 사용 |

#### 정리: 노트북에 만드는 파일
| 파일 | 필수 | 내용 |
|---|---|---|
| `~/.ssh/config` | **필수** | 0-10-2 (접속 이름 `jetson` + 8000 터널 + 연결 유지) |
| `jetson.bat` / `jetson.sh` | 선택 | 0-10-3 (원클릭 접속 + 브라우저) |
| `~/.ssh/id_ed25519(.pub)` | 선택 | 0-10-4 (키 로그인 — 보드 등록은 별도 결정) |
| VS Code `settings.json` 한 줄 | 선택 | 0-10-5 (VS Code 원격 쓸 때만, 주의사항 확인) |

## 1. 시스템 개요

### 1.1 무엇을 하는 시스템인가
종합병원 1층에서 동작하는 **자율주행 안내·접수 로봇**이다. 로봇 위에 터치 화면(키오스크)이 달려 있고,
환자는 화면을 누르거나 말로 다음 두 가지를 할 수 있다.

| 기능 | 환자 입장에서 | 내부 동작 |
|---|---|---|
| **위치 안내** | "내과 어디예요?"라고 말하면 지도에 위치가 표시되고, "네"를 누르면 로봇이 그곳까지 데려다 준다. 도착 5초 뒤 로봇은 혼자 원래 자리로 돌아간다. | 음성인식 → 장소 매칭(규칙 + LLM) → 파일 버스 → Nav2 주행 → 도착 판정 → 자동 복귀 → 방향 정밀 정렬 |
| **접수 안내** | 초진·재진을 고르고 이름·주민번호를 입력한 뒤, AI와 짧게 대화(문진)하면 진료과가 추천되고 대기 순번이 나온다. 호출되면 화면과 음성으로 알려 준다. | 환자 등록/조회 → LLM 대화형 문진(최대 3턴) → 진료과 추천 → 대기명단 → 의료진 화면에서 호출 |

여기에 의료진용 화면 3종(간호사 관리, 의사 진료, 대기실 콜보드)과 4개 언어(한·영·일·중) UI가 붙는다.

### 1.2 전체 구성도
```
 ┌──────────────── 젯슨 AGX Xavier (단일 보드에서 전부 동작) ────────────────┐
 │                                                                         │
 │  [크롬 키오스크 화면]  index.html + app.js (4개 언어 UI)                    │
 │        │  HTTP (localhost:8000)                                          │

 │     ├─ /listen ── 마이크 녹음(에너지 VAD) ──▶ [whisper-server :8080, GPU]    │
 │     ├─ 장소 매칭: 라벨 사전 → 별칭 → OpenAI(gpt-4o-mini)                     │
```

### 1.3 설계상 특징 (논문의 기여점 후보)
1. **엣지 단일 보드 통합**: 자율주행(Nav2), 음성인식(Whisper medium, GPU), 음성합성(MeloTTS, GPU),
   카메라 사람 인식(SegFormer, GPU), 웹 키오스크를 젯슨 한 대에서 동시에 돌린다.
2. **느슨한 결합(파일 버스)**: 웹 앱과 ROS 2를 직접 연결하지 않고 JSON 파일로 주고받는다.
   기존 주행 코드(`nav_request_watcher.py`)를 한 줄도 고치지 않고 도착 감지·복귀·정렬을 별도 노드로 추가했다.
3. **규칙 우선 + LLM 보조**: 장소 매칭과 진료과 추천 모두 규칙(사전·키워드)을 먼저 쓰고,
   실패할 때만 LLM을 부른다. LLM이 꺼져도 시스템은 규칙만으로 동작한다.
4. **안전 우선 문진**: LLM에 진단·병명·약 언급을 금지하고, 질문 수를 최대 2개로 제한한다.
5. **도착 후 폐루프 방향 정렬**: Nav2의 방향 허용오차를 조이는 대신(갇힘 발생), 도착 뒤에
   TF 기반 P제어 + LiDAR 벽면 정렬로 0.5° 수준까지 맞춘다.
6. **개인정보 보호 설계**: 주민번호를 평문으로 저장하지 않는다(마스킹 + SHA-256 해시 + 기기 키 암호화).

## 3. 기동 구조 (전원 → 서비스 → start_all)

### 3.1 2단 기동
전원을 켜면 **브링업까지는 systemd 서비스가 자동으로** 띄우고, 나머지(내비게이션 ~ 앱)는
**스크립트(`start_all.sh` 또는 `start_guide.sh`)를 사람이 실행**한다.

```
전원 ON
 └─ systemd: agv-bringup.service (자동, 부팅 시)
     ├─ [사전1, root] SSD(/mnt/ssd) 마운트 대기 최대 90초 (필요하면 직접 mount)
     ├─ [사전2, root] boot_prep_root.sh: 전원모드 4 고정 → jetson_clocks --fan → 장치 권한(최대 30초 대기)
     └─ [본체, 사용자 wjs] boot_bringup.sh → ros2 launch agv_body agv_bringup.launch.py
사람: 로봇을 '초기 위치'에 세운다
 └─ ./scripts/start_all.sh  (또는 start_guide.sh)
     [1] 장치 준비 (--bringup 옵션일 때만)   [2] ROS 환경
     [3] 브링업 확인(최대 60초 대기)          [4] 내비게이션 (amcl 120초 · bt_navigator 60초 대기)
     [5] 초기 위치 자동 지정                  [6] 복귀 감시 노드
     [6.5] 앱 환경(LLM·관리자 PIN)            [7] run_app.sh: STT → TTS → 마이크 → 앱 서버
사람: 크롬 키오스크 실행
```

### 3.2 부팅 서비스 상세 (`scripts/agv-bringup.service`)
- `After=network-online.target local-fs.target`, `Restart=on-failure`(5초 뒤), `StartLimitIntervalSec=0`(재시도 무제한),
  `KillSignal=SIGINT`(ros2 launch 정상 종료), `TimeoutStopSec=20`.
- `ExecStartPre=+…`의 `+`는 그 명령만 root로 실행하는 systemd 기능이다. 본체는 일반 사용자로 돈다.
- **`RequiresMountsFor`를 쓰지 않은 이유(실측 장애)**: 부팅 시 NVMe 인식이 fstab의
  `x-systemd.device-timeout=5`보다 늦어 마운트가 실패 처리됐고, 의존성 때문에 서비스가 아예 시작되지 않았다
  (2026-09-30). → 서비스 안에서 직접 기다리도록 바꾸고, 설치 스크립트가 fstab 대기를 30초로 늘린다
  (백업·검증·실패 시 원복 포함, `install_boot_bringup.sh:34-48`).
- `boot_prep_root.sh`는 실패해도 항상 `exit 0` — 장치 하나가 없어도 브링업 자체는 막지 않고 로그만 남긴다.

### 3.3 `start_all.sh` 단계별 동작 (`scripts/start_all.sh`, 247줄)
| 단계 | 동작 | 대기/실패 처리 |
|---|---|---|
| 인자 | `--bringup`(선택): 브링업까지 직접 띄움(비상용). 다음 인자 = 앱 포트(기본 8000) | :29-31 |
| [1] | (`--bringup`일 때만) sudo, SSD 마운트, `jetson_clocks --fan`, tty 4개 `chmod 766` | :104-132 |
| [2] | `ros_env.sh` 로드 (Galactic + 워크스페이스, DOMAIN 30, CycloneDDS) | :140-142 |
| [3] | `robot_state_publisher`가 있으면 재사용. 없으면 부팅 서비스를 60초 기다림, 그래도 없으면 종료 | :149-166 |
| [4] | `amcl`이 이미 있으면 건너뜀(**이중 모터 제어 방지**). 없으면 `navigation.launch.py` 실행 | amcl 120초(실패 시 종료), bt_navigator 60초(경고만) |
| [5] | `set_initial_pose.py` — 실패하면 **전체 중단**(위치를 모르는 상태로 주행하면 위험) | :190-193 |

| [7] | `run_app.sh` 포그라운드 실행(`exec` 안 함 → 종료 trap 유지) | :246-247 |

- **준비 확인 방식**: 고정 `sleep` 대신 `ros2 node list`를 2초마다 확인(`wait_for_node`, :84-99).
- **프로세스 그룹 관리**(`start_launch`, :47-58): 런치를 `setsid`로 새 세션에 띄우고, 세션 리더가
  **자기 PID(=PGID)를 파일에 기록한 뒤 `exec`**한다. `$!`를 쓰지 않는 이유는 setsid가 fork하면
  `$!`가 죽은 래퍼 PID가 되어 정리 때 엉뚱한 그룹을 죽일 수 있기 때문이다(:42-45).
- **종료(Ctrl+C) 정책**(:60-80): 이 스크립트가 띄운 그룹만 `SIGINT → 최대 10초 대기 → SIGTERM` 순으로 정리.
  부팅 서비스가 띄운 브링업은 유지한다. STT·TTS 서버도 모델 로딩이 느려 일부러 유지한다(다음 실행 가속).

### 3.4 용도별 기동 스크립트
| 스크립트 | 용도 | 로봇 | STT/TTS | 비고 |
|---|---|---|---|---|
| `start_all.sh` | 전체 운행 | 내비~복귀 | 기동 | `--bringup`으로 브링업까지 |
| `start_guide.sh` | 전체 운행(브링업은 부팅 서비스 전제) | 내비~복귀 | 기동 | 시작·종료 시 **밀린 요청 정리** |
| `start_voice_ui.sh` | 로봇 없이 화면·음성 점검 | 없음 | 기동 | 내비가 떠 있으면 실행 거부(실주행 방지), TTS 대사별 켜기 목록 |
| `start_ui.sh` | 화면만 수정 | 없음 | 떠 있으면 재사용만 | 가장 가벼움 |

**밀린 요청 정리(`clear_pending`, `start_guide.sh:43-61`)** — 실측 버그 대응:
이전 실행에서 실패한 주행 요청·TTS 문장이 다음 실행 때 뒤늦게 실행되는 문제(갑자기 주행, 갑자기 말함)가 있었다.
시작 직전과 종료 시 ① 남은 `nav_request/*.json`을 `nav_request_discarded/`로 옮기고(삭제하지 않음),
② TTS 서버에 `/flush`, ③ STT 녹음 프로세스 종료, ④ 상태 파일을 `idle`로 초기화한다.

### 5.3 카메라 기반 사람 인식 (`hospital_mission/src/vision_obstacle_node.py`)
LiDAR는 사람 다리를 얇은 점으로만 보기 때문에, 카메라로 사람을 찾아 코스트맵에 장애물로 넣는다.
1. 4 Hz 타이머, **2프레임마다 추론**(약 2 Hz). 가운데 정사각형을 잘라 256×256으로 축소.
2. **SegFormer-B1**(ADE20K 학습) 의미 분할, GPU FP16. "person" 픽셀 비율 ≥ 6%면 사람으로 판단.
   2프레임 연속이면 확정, 3프레임 연속 없으면 해제(깜빡임 방지).
3. 사람 영역 아래쪽 30%(발 부분)의 열을 묶어, 그 방향각을 LiDAR 각도로 바꾼 뒤 `/scan_multi`에서
   **±3개 빔 중앙값**으로 거리를 얻는다(0.3~4.5 m만 사용).
4. 사람마다 점 3개(중심 ±0.2 rad)를 `PointCloud2`로 `/people_obstacles`에 발행 → Nav2 표준 장애물 층이 사용.

## 6. 키오스크 ↔ 로봇 연동: 파일 버스와 두 감시 노드

### 6.1 파일 버스 (`/mnt/ssd/cart_ros2/src/llm_package/bus/`)
웹 서버(일반 Python)와 ROS 2 노드는 **같은 폴더의 JSON 파일**로만 소통한다.

| 경로 | 쓰는 쪽 | 읽는 쪽 | 의미 |
|---|---|---|---|
| `nav_request/*.json` | 앱 서버 `/nav`(`kiosk_*`), 복귀 감시(`return_*`) | nav_request_watcher | 주행 요청 대기 중 |
| `nav_request_done/` | nav_request_watcher(목표 **수락** 시 이동) | 앱 서버, 복귀 감시 | 주행 시작됨(도착 아님) |
| `nav_request_discarded/` | clear_pending | (보관용) | 버린 요청 |
| `kiosk_status.json` | 복귀 감시, clear_pending | 앱 서버 `/robot_status` | 로봇 상태·진행률 |

요청 파일 예: `{"place_name":"내과","source":"kiosk","requested_at":…}`

**왜 파일 버스인가**: ① 앱 서버를 ROS 의존 없이 일반 Python으로 둘 수 있고(가상환경 분리),
② 기존 주행 코드를 고치지 않고 기능을 덧붙일 수 있으며, ③ 사람이 파일만 보고 상태를 확인·디버깅할 수 있다.

### 6.2 요청 감시: `nav_request_watcher.py` (기존 코드, 수정 안 함)
- 0.5초마다 `nav_request/`에서 이름순 첫 파일을 집어 **한 번에 하나만** 처리한다.
- 장소 이름 추출 → 이름·별칭 정확 일치, 없으면 부분 문자열 일치 → `NavigateToPose` 액션 전송.
- 목표가 **수락되는 순간** 파일을 `nav_request_done/`으로 옮긴다. 도착 여부(액션 결과)는 로그만 남긴다.
- 액션 서버가 없거나 거부되면 파일이 그대로 남아 0.5초마다 재시도한다 → 3.4절 "밀린 요청" 문제의 원인.

### 6.3 도착 감지 · 자동 복귀 · 방향 정렬: `return_home_watcher.py` (683줄, 새로 작성)
**상태기계**: `IDLE → TRACKING → DWELL → RETURNING → (정렬) → IDLE`

| 단계 | 동작 | 수치(기본값) |
|---|---|---|
| 감지 | `nav_request_done/`에 새 파일 = 주행 시작. 시작 시점 남은 직선거리 저장 | — |
| 진행률 | `progress = 1 − 남은거리/처음거리`(감소하지 않음, 0~1), 0.5초마다 상태 파일에 기록 | W:542-562 |
| 도착 | TF(`map→base_footprint`) 위치가 목표 반경 안 | **0.8 m** (`ARRIVE_RADIUS`) |
| 대기 | 도착 후 대기 → 화면의 도착 안내와 동시에 복귀 | **5초** (`RETURN_DELAY_SEC` = 앱 `ARRIVE_HOLD_MS` 5000) |
| 복귀 | `nav_request/return_*.json` 기록(원자적 쓰기) | 추적 제한 480초 |
| 정렬 | 초기 위치 도착 후 방향 정밀 정렬(아래) | 0.5° |
| 우선권 | 새 사용자 요청이 오면 대기·복귀·정렬을 즉시 중단 | 정렬 루프 안에서도 확인 |

**도착 판정을 Nav2 결과 대신 거리로 하는 이유**: 기존 감시 노드가 액션 결과를 파일로 알려 주지 않기 때문이다.

**방향 정렬 2단계** (Nav2는 방향을 무시하므로 여기서 맞춘다):
1. **정지 확인**: 1.5초 동안 이동 < 0.02 m, 회전 < 1°가 유지될 때까지 기다림(최대 40초).
   → Nav2가 아직 `/cmd_vel`을 내는 중에 끼어들면 **20초 동안 순 회전 1.12°**에 그쳤다(실측).
2. **TF 기반 P제어**(`align_to_yaw`): 각속도 `w = min(0.8, max(하한, 1.2·|오차|))`, 허용오차 0.5°, 제한 90초.
   회전 속도가 8°/s 미만으로 1초 넘게 머물면 하한을 `×1.6 + 0.05`씩 올린다(시작 0.12 rad/s).
   → 이 로봇은 **명령 각속도의 약 12%로만 회전**한다(0.4 rad/s 명령 → 실제 0.048 rad/s, 실측).
3. **LiDAR 벽면 정렬**(`align_to_wall`): 초기 위치에서 AMCL 방향이 약 20° 틀리는 문제(실측) 때문에 추가.
   뒤쪽 180°±35°, 0.3~3.5 m의 점(최소 20개)에 **SVD/PCA로 직선 적합** → 등이 벽과 평행하도록 회전.
   허용오차 0.6°, 제한 60초. 벽을 못 찾으면 1단계 결과 유지.
4. **캐스터 풀기**: 최대 각속도에서도 안 돌면 좌우 ±0.4 rad/s를 0.35초씩 2회 흔든다(최대 3번).
5. 어떤 경로로 끝나든 정지 명령(0 속도)을 3번 발행한다.

### 6.4 초기 위치 자동 지정 (`scripts/set_initial_pose.py`)
RViz의 "2D Pose Estimate"를 사람 대신 한다.
- `map_labels.json`의 "초기 위치" 좌표를 `/initialpose`로 **3번**(0.5초 간격) 발행. 공분산 x·y 0.25 m², yaw 0.0685 rad²(RViz 기본값과 동일).
- 10초 안에 `map→base_footprint` TF가 생기는지 확인하고, 없으면 실패(→ start_all 중단).
  오차가 1 m 또는 25°를 넘으면 경고.

### 6.5 화면 쪽 주행 흐름 (`R`, `A`)
1. `POST /nav` → 요청 파일 생성(좌표 없는 장소는 차단, 파일 안 씀).
2. `/nav_status`를 0.5초마다 최대 30번(약 15초) 확인 → `accepted`면 이동 화면.
3. `/robot_status`를 **0.7초마다**, 최대 480초 확인 → `state=arrived` & 장소 일치면 도착 화면.
4. 이동 화면: 안내도 위 **모식 경로**(L자) 위에 로봇 표시를 진행률만큼 이동, "남은 거리 약 X m(직선)" 표시.
   - 안내도↔지도 좌표 변환을 시도했으나 **불가 판정**: 안내도가 축척도가 아니어서(건물 실측 1:4.28 vs 그림 2.07:1)
     닮음변환 잔차 **RMS 3.79 m**(실측). → 좌표 변환 없이 진행률(비율)만 쓰는 방식으로 대체.
5. 도착 화면 5초 → 처음 화면. 같은 시각 로봇은 복귀 시작.

## 7. 음성 파이프라인 (STT · TTS)

> **2026-10-14 갱신 주의**: 아래 표의 마이크·VAD 설명은 **예전 USB 마이크 기준**이다. 현재는 reSpeaker XVF3800(6ch 중 0번 처리 채널) +
> **Silero VAD(신경망 목소리 판별)**로 바뀌었고, 크기 기준 VAD는 폴백으로만 남아 있다. TTS는 4개 언어·음량 슬라이더 적용 → **0-0절·2.3절** 참고.

### 7.1 기동 (`scripts/run_app.sh` → `scripts/serve.sh`)
1. 마이크를 잡고 있는 이전 프로세스 종료(마이크는 한 프로세스만 사용 가능).
2. **whisper-server**: `ggml-medium.bin`, 127.0.0.1:8080, CUDA. 1초마다 최대 40초 준비 확인.
   `setsid`로 띄워 앱을 꺼도 살아 있게 함(모델 재사용).
3. **TTS 서버**: MeloTTS, 127.0.0.1:5002, `setsid`. 준비를 기다리지 않음(그동안은 브라우저 TTS로 대체).
4. 마이크 자동 감지(`arecord -l`에서 "Usb Audio Device", 웹캠 제외 → `plughw:N,0`),
   자동 이득 끄고 입력 이득 40%(0%면 VAD가 말을 놓침).
5. 앱 서버 `kiosk_server.py` 실행.

### 7.2 음성인식 (STT)
| 단계 | 방법 | 수치 |
|---|---|---|
| 녹음 | `arecord` 스트림, 16 kHz · 모노 · 16bit | S:1051-1068 |
| 발화 검출(VAD) | 0.1초 단위 RMS 에너지 ≥ 임계값이면 음성 | — |
| 임계값 | 서버 시작 때 **1초 주변 소음 측정** → 30 ms 프레임 RMS 하위 20% → `clamp(소음×2.2+120, 350, 1500)` | 실측 소음 RMS 230~278 → 임계 626~731 |
| 끝 판정 | 1.2초 무음이면 종료, 0.6초 미만 버림, 최대 12초 | S:1064-1068 |
| 앞부분 보존 | 말 시작 전 **2.0초**를 미리 버퍼링(첫 음절 약 1.1초가 잘리던 문제 해결) | 기본값 0.3초에서 상향 |

| 후처리 | `difflib` 유사도로 도메인 단어 보정(문장 전체 0.78, 단어별 0.72) | `stt/postprocess.py` |

- **녹음·재생 상호배제**: 로봇이 말하는 동안 녹음하면 자기 목소리를 인식하므로 `_stt_lock`으로 막고,
  화면은 "말씀해 주세요." 재생이 끝난 뒤 녹음을 시작한다(`A:212`).
- 임계값은 시작 때 한 번만 잰다(요청마다 재면 그동안 말 앞부분이 잘림).

### 7.3 음성합성 (TTS, `scripts/tts_server.py`)
- MeloTTS `language="KR"`, GPU. 시작 시 모델 로드 + 워밍업 합성 1회.
- 스피커 자동 감지(카드 **이름**으로 지정 → 재부팅으로 번호가 바뀌어도 유지), 볼륨 80%.
- `POST /tts`(합성+재생), `/synth`(파일만), `/flush`(대기 요청 무효화 + 재생 중단).
- **오래된 요청 폐기**: 들어온 지 25초가 넘은 문장은 재생하지 않음(앱이 30초 기다리다 포기한 문장이
  나중에 엉뚱한 때 들리는 문제 방지). 합성·재생은 하나의 락으로 직렬화.

  목록에 있는 대사만 말한다 — 대사 품질을 하나씩 점검하기 위한 장치.
- TTS 서버가 꺼져 있으면 브라우저 내장 음성(`speechSynthesis`, ko-KR)으로 대체.

## 8. AI 계층: 장소 이해 · 대화형 문진 · 진료과 추천

### 8.1 발화 → 장소 (3단계 연쇄, `S:920-943`)
1. **라벨 사전**(llm_package): `map_labels.json`의 이름·별칭을 정규화(소문자, 공백·문장부호 제거)해
   긴 것부터 **부분 문자열 일치**. 파일이 바뀌면 자동 재로딩.
2. **추가 별칭**(`EXTRA_ALIASES`): 예) "변소"→화장실.
3. **LLM 분류**(`LLM_MATCH_ENABLE=1`이고 API 키가 있을 때만): OpenAI Responses API, `temperature=0`,
   최대 20토큰, 15초 제한. 프롬프트는 "병원 키오스크 장소 분류기" 역할, 동의어·부분이름·오인식·의미상 같은 표현을
   4개 언어 예시로 제시하고 **장소 ID 하나 또는 NONE만** 출력하게 한다. 허용 ID 밖이면 무시.
   - 로그 사례: "where is radiology"→영상의학과, "お手洗いに行きたい"→화장실, "애기가 아픈데…"→소아청소년과.
- "접수/초진/재진…"이 들리면 위치 안내 대신 접수 흐름으로 보낸다(`A:554-556`).
- 일치하면 지도에 위치를 강조 표시하고 "안내를 시작할까요?"를 묻는다. "네"를 누르면 주행(6.5절).

### 8.2 대화형 문진 (`POST /interview`, `S:256-392`)
- **무상태 서버**: 화면이 지금까지의 대화 전체(`messages`)를 매번 보낸다.
- 첫 질문("어디가 불편하세요?")은 고정, 그 뒤 **LLM 꼬리질문 최대 2개**(`MAX_FOLLOWUPS=2`, 총 3턴).
- LLM 출력은 JSON 한 줄 `{"action":"ask","question":…}` 또는 `{"action":"done"}`. 파싱 실패·오류는 모두 `done`.
  설정: temperature 0.2, 최대 120토큰, 20초 제한.
- **프롬프트 핵심**(`S:339-378`):
  - 역할: 의사가 아닌 접수 보조. 진료과를 고르는 데 필요한 최소 정보만 수집.
  - **기본은 종료**. ①답이 애매하거나 ②여러 과가 가능하거나 ③위험 신호 확인이 필요할 때만 질문.
  - 이미 말한 것 재질문 금지, 한 번에 쉬운 질문 하나, 남은 질문 수를 프롬프트에 넣어 줌.
  - **안전 규칙(최우선)**: 진단·병명 추측·약·처방·치료·검사 해석·예후 언급 금지.
    환자가 물으면 "진단과 처방은 의료진이 해드려요. 접수를 도와드릴게요."로 답하고 계속.
  - 환자가 고른 언어로만 답한다.
- 환자는 "이대로 접수하기"로 언제든 문진을 끝낼 수 있다.

### 8.3 종합 · 진료과 추천 (`POST /interview/summarize`, `S:395-413`)
- **진료과**: 키워드 규칙 우선(소아 → 산부인과 → 외과 → 마취통증의학과 → 내과 순), 해당 없으면 LLM 분류
  (5개 외래과 중 하나 또는 NONE; 애매하거나 응급이면 NONE). 영상의학과·진단검사의학과는 의뢰로만 가는 곳이라 제외.
- **요약**: LLM이 ① 의료진용 한국어 요약(`summary_ko`)과 ② 환자 언어로 된 1~2문장 확인문(`recap`)을 만든다.
  "환자가 말한 사실만, 추측·진단·병명·약 금지". 실패하면 발화 원문을 그대로 쓴다.
- 화면: 추천 과 + 나머지 4개 과 선택지 + "진단이 아님" 안내. 요약은 대기명단에 붙어 의료진 화면에 표시된다.

### 8.4 응급 감지 (현재 비활성)
KTAS 1~2 수준 키워드(4개 언어) 기반 응급 필터를 구현했으나 오탐 때문에 사용자 요청으로 끔
(`is_emergency()`가 항상 False, `S:229-231`, `A:604-606`). 키워드 목록과 응급 화면 코드는 남아 있다.

## 9. 병원 업무 시스템 (접수 · 대기 · 의료진 화면 · 개인정보)

### 9.1 환자 흐름
```
[처음 화면] 접수 안내 / 위치 안내  (+ 우상단 국기로 언어 선택)
 ├ 위치 안내 → 마이크 → 인식 → 지도 강조 → "네" → 이동 화면 → 도착 → 5초 뒤 처음 화면
 └ 접수 안내 → "이전에 방문하신 적이 있으신가요?"
     ├ 아니오(초진) → 이름·주민번호 13자리·연락처 → 등록 → AI 문진 → 진료과 추천 → 대기 순번
     └ 네(재진)     → 이름·주민번호 앞 7자리 → 본인 확인
                       ├ 예약 있음 → 자동으로 대기명단 등록
                       └ 예약 없음 → AI 문진 → 진료과 추천 → 대기 순번
[대기 화면] 순번 · 앞 대기 인원 · 진료과, 2.5초마다 갱신. 호출되면 배경이 초록으로 깜빡이고 음성 안내 1회.
```
- 주민번호는 **숫자당 한 칸** 입력(자동 다음 칸 이동). 재진은 뒤 6칸이 `*`로 고정 표시.
- 상단 3단계 진행 표시(초진: 정보 입력/증상/완료, 재진: 본인 확인/확인/완료).

### 9.2 백엔드 API (`kiosk_server.py`, 포트 8000, 요청마다 스레드)
| 분류 | 경로 |
|---|---|
| 음성·안내 | `POST /listen`, `POST /speak`, `GET /goal`, `POST /nav`, `GET /nav_status`, `GET /robot_status`, `GET /config` |
| 접수 | `POST /patient/register`, `/patient/check`, `/reservation/check`, `/interview`, `/interview/summarize`, `/waitlist/add`, `/waitlist/status` |
| 의료진(PIN 필요) | `GET /waitlist`, `GET /doctor/queue`, `POST /patient/remove`, `/reservation/set·remove`, `/waitlist/remove·call·start·done·memo` |
| 공개 | `GET /callboard`, `POST /admin/auth` |

### 9.3 데이터 모델 (`data/*.json`)
| 파일 | 구조 |
|---|---|
| patients.json | `{patients:[{name, rrn_masked, rrn_hash, rrn_enc, contact, created_at, updated_at}]}` |
| reservations.json | `{reservations:{<rrn_hash>:{name, rrn_masked, contact, dept, symptom, date, created_at}}}` |
| waitlist.json | `{queues:{<과id>:[{id, ticket, name, rrn_masked, visit_type, symptom, symptom_summary, status, memo, added_at, called_at, in_progress_at, done_at}]}, counters:{<과id>:int}}` |

- 진료 상태: `waiting → called → in_progress → done`. 완료도 삭제하지 않고 남긴다.
- 순번은 과별로 매기고, 그 과에 대기자가 없어지면 0부터 다시 시작.
- 저장은 임시 파일에 쓴 뒤 이름 바꾸기(원자적), 전역 락 하나로 보호.

### 9.4 개인정보 보호
| 형태 | 용도 | 방법 |
|---|---|---|
| 마스킹 | 화면 표시 | `900101-1******` (앞 6자리 + 성별 1자리) |
| 해시 | 중복 등록 확인·예약 키 | SHA-256 |
| 암호화 | 간호사 화면에서만 전체 번호 확인 | 기기 키(`.rrn_key`, 32바이트, 권한 600) + **HMAC-SHA256 CTR 키스트림 + encrypt-then-MAC**(16바이트 태그, 상수시간 비교) — 외부 라이브러리 없이 구현 |

- 복호화는 PIN 인증된 간호사 관리 화면의 환자 목록에서만 일어난다. 대기·예약·의사 화면은 마스킹만 보인다.
- 재진 본인 확인은 마스킹 7자리 + 이름 비교이며, 조회 결과로 저장된 이름을 돌려주지 않는다.
- 관리자 PIN은 매 요청 헤더로 확인(서버 세션 없음). 화면은 3분 무조작이면 자동 잠금.
- 콜보드에는 순번·이름·상태만 표시(주민번호·증상 요약·메모는 표시 안 함).

### 9.5 의료진 화면
| 화면(URL) | 사용자 | 기능 |
|---|---|---|
| `?nurse=1` (예전 `?admin=1`도 호환) | 간호사 | PIN → 탭 3개(환자 목록[전체 주민번호]·예약 관리·과별 대기명단), 호출/재호출·완료·삭제, 5초 자동 갱신 |
| `?doctor=1` | 의사 | PIN → 진료과 선택(5개) → 대기 카드(순번·이름·마스킹 번호·초진/재진·AI 요약), 호출·진료 시작·완료·메모, 3초 갱신 |
| `?callboard=1` | 대기실 모니터 | 과별 열에 "N번 · 이름 · 호출/진료중", 2.5초 갱신 |

### 9.6 다국어 · 화면 디자인
- 4개 언어(한·영·일·중). 동적 문구는 `tt(ko,en,ja,zh)`, 고정 문구는 `data-i18n` 속성.
  국기 버튼(접이식)으로 선택, 브라우저에 저장. LLM 문진도 선택한 언어로 답하고, 의료진 요약은 항상 한국어.
- 디자인 토큰(`src/css/tokens.css`): 따뜻한 배경색, 주색 `#2b6ca0`(흰 글자 대비 5.59:1), 터치 최소 크기 64px,
  대비 ≥ 4.5:1, 색만으로 정보 전달 금지. 글꼴은 Noto Sans CJK KR로 4개 언어 통일, 국기는 Noto Color Emoji.
- 무조작 자동 초기화 기능은 구현돼 있으나 현재 꺼 둠(`IDLE_DISABLED=true`, 2026-10-02).

## 10. 개발 중 얻은 실증 결과와 교훈 (논문 결과·고찰용)

> 아래는 개발 과정에서 **실제로 측정하거나 겪은** 사실이다. 논문의 "구현 중 문제와 해결" 또는 "고찰"에 쓸 수 있다.
> 다만 대부분 1회성 관찰이므로, 정량 결과로 쓰려면 12장의 방법으로 다시 측정하는 것을 권한다.

### 10.1 전원 · 열 · 계산 자원
- **모터 구동 순간 젯슨만 꺼지는 현상**(LiDAR는 계속 회전): 전원 기록기(`jetson_monitor.py`, INA3221 0.2초 간격 +
  매 샘플 fsync)로 기록. 꺼지기 직전 입력 전압 최저 18.4 V, 5 V 레일 최저 4.99 V.
  전원 모드를 **MAXN → MODE_30W_6CORE**로 낮추자 재현되지 않았다 → 최대 성능 모드의 순간 전력 요구가
  모터 기동과 겹쳐 생긴 전원 마진 부족으로 판단. 부팅 서비스가 매번 이 모드를 강제한다.
- **30W/6코어 모드에서의 CPU 포화**(2026-09-30 측정): 6코어 모두 96~100%.
  주요 점유: IMU 드라이버 약 143%(1 ms 타이머), 카메라 사람 인식 약 75%(메모리 3.2 GB), VS Code 약 75%,
  RViz 약 57%, EKF·AMCL·경로계획 각 20~30%.
- 그 상태에서 음성 지연: **TTS 한 문장 5.9초**, **STT 3초 발화 인식 10.3초**(인식 결과는 정확).
  평상시 로그의 whisper 응답은 0.87~1.10초(이상치 4.89초 1회).
- TTS 서버 준비 시간: 평상시 로드 9.9초 + 워밍업 18.5초 / CPU 포화 시 49.1초 + 93.8초.

### 10.2 주행 · 위치추정
- **Nav2 방향 허용오차를 조이면 안 된다**: 목표 방향을 맞추려 회전을 반복하다 복구 동작에 갇혀 목표가
  끝나지 않았다 → 방향은 무시하고(yaw 3.14159) 도착 후 별도 정렬로 해결.
- **다른 제어기가 주행 중일 때 `/cmd_vel`에 끼어들면** 서로 명령이 섞여 20초 동안 순 회전 1.12°에 그쳤다.
- **실제 회전은 명령 각속도의 약 12%**(0.4 → 0.048 rad/s) → 회전율을 재며 각속도 하한을 자동으로 올리는 방식 도입.
- **초기 위치에서 AMCL 방향 오차 약 20°** → LiDAR로 등 뒤 벽면을 직선 적합해 정렬하는 2단계 추가.
- **목표 좌표가 지도의 자유 공간 밖이면** Nav2가 도착 반경(0.8 m) 밖에서 멈춰 복귀·정렬이 시작되지 않는다
  (예: 초기 위치 오른쪽은 벽까지 0.25 m뿐인데 1 m 이동 요청 → 실패).
- **LiDAR 2대가 동시에 시간 초과** = 전원 문제 신호(USB-UART는 USB 전원만으로도 장치가 인식됨).

### 10.3 통신 · 프로세스
- **와이파이(폰 핫스팟) 끊김 → 전체 ROS 통신 정지**(2026-09-30): DDS가 브링업 시점의 무선 인터페이스로
  데이터를 보내고 있어, 핫스팟이 7분간 끊기자 TF·오도메트리·LiDAR가 다른 노드에 전달되지 않았고
  초기 위치 지정이 실패했다. 모든 노드가 한 보드에 있으므로 `ROS_LOCALHOST_ONLY=1`로 고정하면 해결 가능(미적용, 11장).
- **이전 실행의 실패 요청이 다음 실행 때 실행되는 문제**: 3.4절·6.2절 참조 → 시작·종료 시 정리 + TTS 오래된 요청 폐기.
- **부팅 서비스 미기동**: NVMe 인식 지연 vs fstab 5초 제한(3.2절).
- 음성 서버를 같은 프로세스 그룹에 두면 앱 종료(Ctrl+C) 때 같이 죽는다 → `setsid` + 세션 리더가 자기 PID 기록.

### 10.4 음성 · UI
- 말 시작 앞부분 약 1.1초가 잘림 → VAD 앞부분 버퍼 0.3초 → 2.0초.
- 오인식(원목과→원무과, 내권→내과) → whisper 초기 프롬프트에 진료과 이름 주입 + 유사도 후처리.
- 마이크 입력 이득 0%면 VAD가 말을 못 잡음 → 40% 고정, 자동 이득 끔.
- 젯슨에 기본 글꼴(Noto Sans KR)이 없어 **영어 화면만 다른 글꼴(DejaVu)**로 그려지고 줄 높이가 달라졌다
  (제목 66 → 54 px) → 설치된 Noto Sans CJK KR 지정으로 4개 언어 통일.

## 11. 한계 · 코드상 불일치 · 미검증 항목 (논문에 쓰기 전 확인)

### 11.1 기능상 한계
1. **STT는 한국어 고정**(`language=ko`, S:1020). UI는 4개 언어지만 음성 입력은 한국어만 정확하다.
2. **TTS도 한국어 모델뿐**: 영·일·중 문장도 한국어 MeloTTS로 보내지고, 브라우저 대체 음성도 ko-KR 고정.
3. **확인 단계가 실제로는 실행되지 않음**: 서버 신뢰도는 0.95(일치) 또는 0.3(불일치) 두 값뿐인데, 화면의
   "맞나요?" 확인 구간은 0.5~0.85라 도달하지 않는다.
4. **도착 판정은 거리(0.8 m)만** 본다. Nav2 실패 결과는 복귀 감시 노드에 전달되지 않는다.
5. 위치 복원은 **방향만** 정밀 정렬한다(위치는 Nav2 허용오차 0.45 m 수준).
6. 카메라 사람 인식 노드 설명에 있는 **속도 제한(`/speed_limit`)은 미구현**(주석에만 존재).
7. 응급 감지는 꺼져 있다(코드는 남아 있음). `/triage` 엔드포인트도 화면에서 쓰지 않는다.
8. 무조작 자동 초기화가 꺼져 있어, 환자가 중간에 떠나면 다음 사람이 "처음으로"를 눌러야 한다.

### 11.2 보안상 고려할 점
1. 주민번호 해시는 **솔트 없는 SHA-256** → 주민번호 공간이 작아 무차별 대입에 약하다.
2. 재진 본인 확인이 마스킹 7자리 + 이름이라 동명이인·같은 생년월일 충돌 가능.
3. 기본 PIN이 "0000"(`.admin_pin`이 없으면), PIN 비교가 상수시간이 아님.
4. `/patient/check`, `/waitlist/add`는 PIN 없이 호출 가능(키오스크 특성상 의도된 공개).
5. 콜보드에 이름 전체 표시(사용자 결정). 코드 주석 일부("개인정보 없음")가 실제 동작과 다르다.

### 11.3 설정값 불일치 (수치를 논문에 쓰기 전 실측 필요)
1. **바퀴 간격 값이 세 가지**: 모터 0.475 m / 오도메트리 0.46 m / URDF 0.48 m. 바퀴 반지름 값은 없고 둘레(0.15 m)만 있음.
2. **로봇 반경**: 지역 코스트맵 0.4 m / 전역 0.3 m, 실제 외곽(footprint) 다각형 미정의.
3. LiDAR 모델(A3)은 실행 파일 이름과 통신 속도로만 추정. 앞/뒤 포트 대응이 다른 런치 파일과 반대로 적혀 있다.
4. 카메라-LiDAR 각도 오프셋 63.11°에 "실측 후 조정 필요(TODO)" 주석. 초점거리를 640px 기준으로 계산해
   256px 분할 결과에 적용한다.
5. BT Navigator가 융합 오도메트리(`/odometry/filtered`)가 아닌 휠 오도메트리(`/odom`)를 쓴다.
6. `map_labels.json`의 `track` 목표와 사각형 영역 좌표가 지도 범위 밖에 있다(사각형은 쓰이지 않음).
7. 지도(`my_map.pgm`)를 만든 SLAM 방법이 기록돼 있지 않다(slam_toolbox·Cartographer 설정 둘 다 존재).
8. 내부 ID 중 `wonmu`=산부인과, `pharmacy`=영상의학과는 과거 이름이 남은 것 → 논문에는 한국어 과 이름 사용.
9. 런치 파일이 `nav_request_watcher`에 넘기는 파라미터를 노드가 읽지 않는다(경로가 코드에 고정).
10. `IMU` 드라이버의 CPU 점유(약 143%)가 비정상적으로 높다(1 ms 타이머로 추정, 미조사).

## 12. 논문 구성 제안과 추가로 측정할 것

### 12.1 구성 제안
1. 서론: 병원 안내·접수 인력 부담, 다국어 환자, 기존 키오스크의 한계
2. 관련 연구: 병원 안내 로봇, 음성 기반 HRI, LLM 기반 문진/트리아지, 엣지 AI
3. 시스템 설계: 1.2절 구성도, 1.3절 설계 원칙(파일 버스, 규칙+LLM, 안전 우선)
4. 구현: 4~9장 (하드웨어 → 주행 → 연동·정렬 → 음성 → AI → 병원 업무)
5. 실험: 아래 12.2절
6. 고찰: 10장(전원·연산 제약, 정렬 문제, 통신 장애, 개인정보), 11장 한계
7. 결론

### 12.2 논문용으로 새로 측정하면 좋은 것 (현재 정량 데이터 부족)
| 지표 | 방법 제안 |
|---|---|
| 장소 인식 정확도 | 장소별 발화 문장 세트(예: 10개 장소 × 화자 N명 × 3회)로 ① 규칙만 ② 규칙+LLM 비교 |
| 응답 지연 | `/listen` 전체(녹음 종료→결과), whisper 단독, LLM 단독, TTS 합성 시간(`synth_sec`) 기록 |
| 주행 성공률·시간 | 장소별 왕복 N회: 도착 성공, 소요 시간, 도착 위치 오차 |
| 복귀 정렬 정밀도 | 정렬 전후 방향 오차(로그 + 바닥 표시로 실측), 정렬 소요 시간, 캐스터 풀기 횟수 |
| 문진 품질 | 증상 시나리오 세트로 추천 진료과 정확도, 평균 질문 수, 안전 규칙 위반(진단 언급) 0건 확인 |
| 자원 사용 | tegrastats로 CPU/GPU/메모리/전력(전원 모드별), 동시 실행 시 음성 지연 변화 |
| 사용성 | 실제 사용자(또는 대리 사용자) 과제 수행 시간, SUS 설문 |

> 측정 전에 11.1-3(확인 단계 미작동), 11.3-1·2(기구 수치 불일치)를 정리하면 실험 해석이 깔끔해진다.
> 와이파이 의존(10.3)은 `ROS_LOCALHOST_ONLY=1` 적용 후 측정하는 것이 안전하다.

## 13. 운영 요약 (명령어)

```bash
# (최초 1회) 부팅 자동 브링업 설치 — 이후엔 전원만 켜면 브링업 자동
sudo /mnt/ssd/projects/myproject/scripts/install_boot_bringup.sh

# 운행: 로봇을 '초기 위치'에 세운 뒤
cd /mnt/ssd/projects/myproject
./scripts/start_guide.sh            # 또는 ./scripts/start_all.sh (Ctrl+C로 종료, 브링업은 유지)

# 화면 (다른 터미널)
chromium --user-data-dir=/tmp/k-patient --kiosk "http://localhost:8000/"
#   간호사 ?nurse=1 · 의사 ?doctor=1 · 대기실 ?callboard=1

# 로봇 없이 화면·음성 점검
./scripts/start_voice_ui.sh         # 대사별 음성 켜기: tts_enabled.txt

# 상태 확인
systemctl status agv-bringup        # 로그: logs/boot_prep.log, logs/bringup.log
tail -f logs/return_home.log        # 도착·복귀·정렬
curl localhost:8000/robot_status    # 로봇 상태·진행률
sudo python3 scripts/jetson_monitor.py   # 전원·온도 기록(브라운아웃 진단)
```
